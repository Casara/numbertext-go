# AGENTS.md

Guidance for AI coding agents working in this repository. `CLAUDE.md`
imports this file (`@AGENTS.md`) rather than duplicating it, so Codex,
Cursor and Claude Code all read the same instructions from one place.
See [README.md](README.md) / [README.pt-BR.md](README.pt-BR.md) for the
user-facing overview.

## What this is

`numbertext-go` spells out numbers as words (cardinals, ordinals, gender
variants, negatives, currency amounts) in every language shipped by
[Numbertext.org](https://numbertext.github.io/) (upstream:
[libnumbertext](https://github.com/Numbertext/libnumbertext)). Rather than
hand-writing per-language conversion code, it interprets the same `.sor`
rule files upstream ships, written in a small regex-rewriting DSL called
**Soros**. Adding a language is a data change (`data/<code>.sor`), never a
code change.

## Architecture

```text
internal/soros/   the Soros language interpreter (generic, no numbertext-specific concepts)
  lexer.go         comment/language-line filtering, statement splitting, quoting, pattern/value split
  template.go      parses a rule's replacement text into an AST (literal/backref/call/optional/pipe)
  escape.go        hides/reveals the spec's backslash-escaped special characters
  program.go       Compile(): builds the ordered rule list, macro-prefix concatenation, hidden left-zero rule
  regex.go         compilePattern(): RE2 first, regexp2 fallback (timeout-bounded) only for patterns RE2 can't express
  eval.go          Run()/run(): the recursive evaluator (first full-match rule wins, boundary propagation)

numbertext.go     public API: Cardinal/Ordinal/Year/Currency/Money/Help/Convert/RegisterLocale
locales.go        registry type: lazy compile-and-cache per language code, RegisterLocale
                  (a regional code like "en-GB"/"pt-BR" falls back to the base
                  file "en"/"pt" but still compiles with the full code, so the
                  base file's "[:en-GB:]"/"[:pt-BR:]"-tagged lines take effect)
locale_all.go     //go:embed data/*.sor (default build: every language, see below)
locale_<code>.go  one file per language, generated by scripts/gen-locale-embeds.py,
                  each embedding just data/<code>.sor behind a pair of build tags
                  ("numbertext_select" + "numbertext_lang_<code>") — see "Selecting
                  which languages get embedded" in README.md. All of these (and
                  locale_all.go) only ever call registry.register(); which set of
                  files actually compiles is entirely decided by build tags, so
                  there is no reg-construction ordering to reason about.
cmd/numbertext/   CLI wrapper, also doubles as a runnable usage example
data/*.sor        upstream rule files, byte-for-byte, see data/SOURCE.md for provenance
```

`internal/soros` knows nothing about numbers, currencies, or languages —
it is a general interpreter for the Soros language. Everything
numbertext-specific (which section name means "ordinal", how a currency
amount string is built) lives in the root package.

## The Soros language, condensed

Full spec: `doc/sorosspec.pdf` in the upstream repo (fetched and read
while building this port; not vendored here). The essentials:

- A program is one flat, ordered list of `pattern → template` rules,
  always matched as a **full match** against the current input string.
  First match wins.
- `== prefix ==` defines a **macro**: the prefix text is concatenated (as
  literal regex text, with `^` hoisted to the front when present) onto
  every following rule's pattern, until the next `==`. There is no
  separate namespace per prefix — `$(ordinal 123)` just re-runs the whole
  rule list against the literal string `"ordinal 123"`, and whichever
  macro-prefixed rule matches that literal text wins.
- Template syntax: `\N` (raw backreference, N=0-9, no re-evaluation),
  `$N` (sugar for `$(\N)`), `$(...)` (recursive call to the whole engine
  on a constructed argument), `[...]` (conditional text — kept only if
  the call(s) inside are non-empty), `|` (boundary-modifier marker
  adjacent to a call — forces leading/trailing-boundary eligibility
  regardless of position, e.g. for `negative |$1` after stripping a sign).
- A hidden rule is always active: `([a-z][-a-z]* )?0+(0|[1-9]\d*)` →
  `$(\1\2)`, stripping extra leading zeros (also after a macro-prefix
  word).

## Regex engine: RE2 first, regexp2 as a bounded fallback

`compilePattern` (`internal/soros/regex.go`) tries Go's standard
`regexp` (RE2) first — linear-time in the input length, guaranteed, and
what every rule but a handful across all of `data/*.sor` compiles
under. RE2 deliberately excludes backreferences and lookaround; a small
number of real-world locale files genuinely need them (e.g. `hu.sor`'s
grammatical-suffix "database" lookup, `.*:\1:(-[^-:]*).*` — a
backreference to a group defined earlier in the same pattern, the same
class of construct the reference C++/Java/Python implementations'
native backtracking engines handle natively). For exactly the patterns
RE2 refuses to compile, `compilePattern` falls back to
[`regexp2`](https://github.com/dlclark/regexp2) (a ported .NET/PCRE-style
backtracking engine), with `MatchTimeout` set to
`fallbackMatchTimeout` so a pathological pattern degrades to "this rule
doesn't match" instead of hanging — the standard mitigation for
backtracking's catastrophic-case risk (ReDoS), and the reason this
fallback is scoped to only the rare patterns that need it rather than
replacing RE2 everywhere: the overwhelming majority of rules keep RE2's
stronger guarantee.

An earlier design considered here and rejected: matching a
backreferenced pattern by compiling a "probe" (the backreference
position replaced by a plain copy of the referenced group's own
pattern) under RE2, then verifying group equality after the fact. That
works for a backreference to a group with no real matching ambiguity
(true for every backreference in `data/*.sor` today), but is provably
incomplete in general — `regexp.MustCompile` chooses one match
deterministically, and for a pattern like `(a+)\1` against a string
with more than one way to split it, that single candidate split can
fail the equality check even though a valid split exists elsewhere,
which a true backtracking engine would find. Given the project's own
requirement that this port have the same regex capability as the
reference implementations, this false-negative risk wasn't acceptable
even though the concrete `.sor` files in `data/` don't currently trigger
it.

## Resolved: `bg.sor`'s one non-nesting rule was a data typo, not a parser gap

`Compile` used to skip one `bg.sor` rule whose `[...]`/`$(...)` didn't
nest as a tree: `[ $(and:$(ordinal \2)])` — the bracket's `]` sits
inside the call's still-open parens, so the call's own paren-matching
(which correctly ignores `]`) consumes it as part of its own argument
text before the bracket's scan ever sees it as a closer.

Two engine-side fixes were considered and rejected before looking at
the data itself:

- **Loosening the parser to tolerate crossing `[...]`/`$(...)` spans**:
  rejected because there's no principled tree for a genuine crossing —
  building one means either picking an arbitrary resolution or
  bit-for-bit replicating the reference Python/Java implementations'
  own resolution, which turns out to be a side effect of *which text
  substitution pass happens to run first* in their pipeline (`[...]` is
  resolved via an earlier, paren-agnostic pass, before any
  `$(...)`-paren counting starts) rather than a documented semantic —
  an implementation accident isn't a foundation worth encoding
  permanently into the interpreter.
- **A `hu.sor`-style engine-level workaround**: didn't apply here in
  the first place — this was never a regex-engine limitation (see
  above); it's purely in the template grammar, which no choice of
  regex engine touches.

Both were the wrong layer to fix it in. Comparing the broken line
against its immediate neighbor — `1([0-9]{3}) хиляда[
$(and:$(ordinal \1))]`, the singular counterpart, correctly nested —
showed the "crossing" was never intentional: upstream's line ends
`\2)])` (bracket before the second closing paren) where the sibling
rule (and the general `$(eN:\1)[ $(and:$2)]` shape every other
magnitude uses) has `))]`. That's a two-character transposition, not a
deliberate construct — verifiable by inspection against a rule that
already works, not a guess about intent. So the fix went into
`data/bg.sor` itself (`\2)])` → `\2))]`), documented and reproduced on
every future sync in `data/SOURCE.md`'s "Local patches" section and
`scripts/sync-data.sh`, with a plan to submit it upstream so the patch
step (and this section) can eventually go away. `bg.sor` now compiles
with zero skipped rules.

The general principle stands unchanged for whatever the *next* skipped
rule turns out to be: a rule `Compile` can't parse is recorded and
never guessed at. What changed here is recognizing that this
particular "can't parse" was upstream's bug, not this port's
limitation — worth checking before assuming the fix belongs in Go code
at all.

## Working in this repo

- **Verify locale output before writing it down.** The rule files
  encode real per-language stylistic choices that are easy to get wrong
  by intuition alone. In `en.sor` alone: plain `en` omits "and" in "one
  hundred one" while `en-AU`/`en-GB`/`en-IE`/`en-NZ` include it;
  `Cardinal("1001")` is "one thousand and one" (the separator function
  inserts "and" before a sub-100 remainder); but `Year("2001")` is "two
  thousand one" — the `year` section runs its cardinal result through a
  `year-remove-and` pass that plain `Cardinal` never sees. When adding
  test expectations, run the actual code
  (`go run ./cmd/numbertext -lang <x> -cardinal <n>` or a throwaway test)
  and confirm the result is reasonable, rather than guessing.
- **Engine changes**: validate against `internal/soros/soros_test.go`
  first (the spec's own canonical examples — string reversal, thousands
  separator, Devanagari digits — plus targeted boundary/bracket/macro
  cases) and `regex_test.go` (the RE2/regexp2 fallback boundary) before
  touching real locale files. If engine tests pass but a real `.sor`
  file misbehaves, that's a signal the spec has a subtlety the unit
  tests don't cover yet — add a minimal reproduction there.
- **Don't hand-edit `data/*.sor`.** These are synced verbatim from
  upstream (see `data/SOURCE.md`); fix bugs in the interpreter, not the
  data — unless the data is actually wrong, as in the one documented,
  narrowly-justified exception in `data/SOURCE.md`'s "Local patches"
  section (a verifiable upstream typo, not a judgment call). Use
  `scripts/sync-data.sh` to refresh from upstream; it reapplies that
  patch automatically.
- **Don't hand-edit `locale_<code>.go`.** These are generated by
  `scripts/gen-locale-embeds.py` from the current `data/*.sor` file list
  (each carries a "Code generated ... DO NOT EDIT" header). Re-run that
  script after adding/removing a `data/*.sor` file — it also deletes
  stale generated files for languages no longer present. `locale_all.go`
  is hand-written and not touched by it.
- Code comments and identifiers are English-only, even though the
  project's docs ship in English and pt-BR (see README.md /
  README.pt-BR.md).
- Code conventions beyond what `gofmt`/`goimports`/`golangci-lint`
  already enforce (error wrapping via `wrapcheck`, explicit
  dependencies, when to prefer the vertical call format) are in
  [docs/coding-style.md](docs/coding-style.md) /
  [docs/coding-style.pt-BR.md](docs/coding-style.pt-BR.md).

## Commands

`make help` lists every command with a one-line description. Before opening
a PR, run:

```sh
make check     # lint + arch-lint + verify-docs + tests with the race detector + test-select
make lint-md   # markdown lint (requires Node.js >= 20)
```

That's the minimum CI runs on every PR ([.github/workflows/ci.yml](.github/workflows/ci.yml)),
split there across separate jobs rather than one `make check` call:
`lint`/`arch-lint`/`verify-docs` only need to run once, since their
result doesn't depend on which Go version runs them, while
`test-race`/`test-select` run once per entry in the Go version matrix.
Running the former inside that matrix too used to just waste CI time,
until it broke outright the day `golangci-lint` raised its own floor
past this project's declared one (see the version-pin comments next to
`GOLANGCI_LINT`/`GO_ARCH_LINT` in the `Makefile`, and the `lint` job's
own comment in `ci.yml`) - the failure mode this split now prevents.
See [CONTRIBUTING.md](CONTRIBUTING.md) for the full workflow (commit
convention, branch/PR process, doc-sync expectations).

`make doc-sync` prints which documentation a diff touching the exported
API has not touched (`README.md`/`README.pt-BR.md`, `AGENTS.md`,
`CHANGELOG.md`, and `skills/using-numbertext-go/SKILL.md`). It never
fails: a change can legitimately leave all of them alone, and a check
that cried wolf would be ignored. A `Stop` hook in `.claude/settings.json`
surfaces the same output at the end of a turn.

For a closer look, the `api-surface-reviewer` subagent (`.claude/agents/`)
reads the diff in a clean context and reports what changed in the
exported API with `file:line`, and which documentation contradicts it.
`bilingual-doc-reviewer` (same directory) does the equivalent check
between an English doc and its `.pt-BR.md` twin — broken cross-links, a
bullet added to one side and not the other.
